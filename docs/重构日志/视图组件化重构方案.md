# 视图组件化重构方案（Component Refactoring）

> **创建日期**: 2026-03-01
> **分支**: `refactor/view-componentization`
> **状态**: 方案讨论阶段 · 待评审

---

## 一、问题陈述：为什么必须重构？

### 1.1 现状病理诊断

当前的双列视图是在**单体窗口架构**之上，以"打补丁"方式扩展出来的。主要病灶如下：

| 病灶 | 表现 | 根因 |
|------|------|------|
| **主/副不对等** | `ColumnInteractionHandler` 需要两套实例，`ColumnService` 每个方法都需要 `IsSecondary` 判断 | 副面板是后期强行嫁接的"二等公民"，不具备与主面板同等的生命周期管理 |
| **配置爆炸** | `AppConfig` 中每个列属性都有 `_Secondary` 后缀的影子字段，共计 11 个重复属性 | 配置层未能抽象出"面板实例"的独立状态容器 |
| **中枢偏心** | `MainWindow` / `WindowOrchestrator` / `NavigationModeUIAdapter` 内部大量 `if (isSecond)`  分支 | 编排层只为主面板设计，副面板通过边角逻辑搭便车 |
| **预览面板强绑定** | `RightPanelViewModel` 在双列模式时被完全隐藏（`IsDualListActive → false`），无法为任一面板提供预览 | 预览面板未被设计为可组合的独立组件 |
| **无法交换位置** | 不存在"左↔右互换"的能力，因为代码中硬编码了主=左、副=右的定位 | 面板身份与其物理位置紧耦合 |

### 1.2 核心目标

1. **消灭"主/副"概念** — 所有面板在代码中一律平等，均为同一个 `BrowserPane` 类的实例。
2. **支持面板左↔右调转** — 一键交换两个面板的物理位置（及其全部状态）。
3. **支持面板级独立预览** — 预览面板不再是全局唯一的右侧栏，而是可为任一 `BrowserPane` 附加的可组合子组件。
4. **配置自包含** — 每个面板实例携带自己的完整状态快照，无需全局 `_Secondary` 字段。

## 二、核心术语重命名

| 旧名称 | 新名称 | 说明 |
|--------|--------|------|
| PrimaryPane / SecondaryPane | `Pane A` / `Pane B`（代码层 `Panes[0]` / `Panes[1]`） | 对等身份，仅描述位置，不描述主从 |
| FileBrowser / SecondFileBrowser | 统一为 `BrowserPane.Browser` | 面板的内部组件，不在窗口层暴露 |
| RightPanel（预览面板） | `PreviewAttachment` | 强调它是可附加到任意面板上的独立组件 |
| IsSecondary | **删除** | 不再存在此概念 |
| ColumnInteractionHandler / SecondColumnInteractionHandler | 统一为 `BrowserPane.ColumnHandler`（实例内部自带） | 无需外部区分 |

## 三、方案对比分析

### 方案 A：渐进式迁移 — 抽象 `IPaneContext` 接口

**核心思路**：不重写 `FileBrowserControl`，而是在现有架构之上抽取一个 `IPaneContext` 接口，使所有面板相关的服务（列管理、标签页、文件列表、预览）都通过此接口获取上下文。

```
┌─ MainWindow ─────────────────────────────────────┐
│                                                   │
│  ┌─ IPaneContext[0] ──────┐  ┌─ IPaneContext[1] ──────┐
│  │  FileBrowserControl    │  │  FileBrowserControl    │
│  │  ColumnHandler         │  │  ColumnHandler         │
│  │  TabService            │  │  TabService            │
│  │  PaneState (config)    │  │  PaneState (config)    │
│  │  PreviewAttachment?    │  │  PreviewAttachment?    │
│  └────────────────────────┘  └────────────────────────┘
│                                                   │
│  ┌─ PaneManager ──────────────────────────────────┐
│  │  Panes: IPaneContext[]                         │
│  │  ActivePane: IPaneContext                      │
│  │  SwapPanes()                                   │
│  │  AttachPreview(paneIndex)                      │
│  │  DetachPreview(paneIndex)                      │
│  └────────────────────────────────────────────────┘
└───────────────────────────────────────────────────┘
```

**优点**：
- 改动范围可控，可分阶段渐进式落地
- 不影响 XAML 布局，只重构 C# 代码层
- 面板数量可动态扩展

**缺点**：
- 仍然依赖 `MainWindow` 作为宿主容器
- `FileBrowserControl` 的内部逻辑仍然保持原样，只是包装层变薄

---

### 方案 B：深度重构 — `BrowserPane` 自治组件

**核心思路**：将 `FileBrowserControl` + `TabManagerControl` + `ColumnInteractionHandler` + `PaneState` 融合为一个完全自包含的 `BrowserPane` 组件。每个 `BrowserPane` 是一个独立的 UserControl，携带自己的 ViewModel、列管理器、标签页服务、和可选的预览附件。

```
┌─ MainWindow (纯粹的 Shell 容器) ─────────────────┐
│                                                   │
│  ┌─ BrowserPane A ─────────────────────────┐      │
│  │  ┌─ BrowserPaneViewModel ────────────┐  │      │
│  │  │  PaneState (columns, tabs, nav)   │  │      │
│  │  │  FileListViewModel               │  │      │
│  │  │  ColumnService (实例化)            │  │      │
│  │  └──────────────────────────────────┘  │      │
│  │  ┌─ TabManagerControl ───────────────┐  │      │
│  │  └──────────────────────────────────┘  │      │
│  │  ┌─ FileBrowserControl ──────────────┐  │      │
│  │  │  AddressBar                       │  │      │
│  │  │  FileList (GridView)              │  │      │
│  │  │  InfoBar                          │  │      │
│  │  └──────────────────────────────────┘  │      │
│  │  ┌─ PreviewAttachment? ──────────────┐  │      │
│  │  │  (可选，独立 UserControl)          │  │      │
│  │  └──────────────────────────────────┘  │      │
│  └─────────────────────────────────────────┘      │
│                                                   │
│  ┌─ BrowserPane B ─────────────────────────┐      │
│  │  (结构完全相同，PaneState 不同)          │      │
│  └─────────────────────────────────────────┘      │
│                                                   │
│  PaneOrchestrator:                                │
│    swapPanes(), attachPreview(), detachPreview()   │
└───────────────────────────────────────────────────┘
```

**优点**：
- 彻底消除 `IsSecondary` / `_Secondary` / 双 Handler 等结构性冗余
- `BrowserPane` 完全自治，未来可以"三列""四列"甚至"浮动窗口"
- 预览面板成为面板的内部子组件，位置、可见性均由面板自身控制
- 交换面板只需交换 `Grid.Column` 绑定值

**缺点**：
- 工程量较大，涉及 XAML、ViewModel、Orchestrator、Handler 四个层面的改造
- 需要重新设计 `PaneState` 的持久化策略（当前 `AppConfig` 的平铺结构需要改为数组或字典）

---

### 方案 C：混合策略 — B 的目标 + A 的节奏

**核心思路**：以方案 B 为最终目标架构，但采用方案 A 的渐进式落地路径。分 4 个阶段逐步蜕变：

#### 阶段 1：统一面板状态容器（最低风险）
- 将 `AppConfig` 中的 11 个 `_Secondary` 字段合并为 `PaneState[]` 数组
- `ConfigMapper` 改为遍历数组进行映射
- 现有代码通过 `PaneState[0]` / `PaneState[1]` 索引访问
- **不改 UI 层和 Handler 层**

#### 阶段 2：引入 `PaneContext` 中间层
- 创建 `PaneContext` 类，封装 `FileBrowserControl` + `ColumnInteractionHandler` + `TabService` + `PaneState`
- `MainWindowViewModel` 持有 `PaneContext[]` 而非裸 `PrimaryPane` / `SecondaryPane`
- `WindowOrchestrator` 对面板的所有操作改为通过 `PaneContext` 统一分发
- **实现面板交换功能**（交换两个 `PaneContext` 的 `Grid.Column`）

#### 阶段 3：`BrowserPane` 自治组件化
- 将 `PaneContext` 升级为 `BrowserPane` UserControl
- 把 `FileBrowserControl` + `TabManagerControl` 的 XAML 合并到 `BrowserPane.xaml`
- `ColumnService` 从全局单例改为面板实例成员
- **全面消除 `IsSecondary` / `_Secondary` 残留**

#### 阶段 4：预览面板可组合化
- 将 `RightPanelViewModel` 重构为 `PreviewAttachment`
- 每个 `BrowserPane` 可以通过一个 `AttachPreview()` 方法挂载独立的预览子面板
- 预览面板的位置（底部/右侧/浮动）由 `BrowserPane` 的 `PreviewMode` 属性控制

## 四、面板交换功能详细设计

### 4.1 交互方式

在双列模式下，两个面板之间的分割条（Splitter）上放置一个**交换按钮** `⇄`（或使用更优雅的双箭头图标）。

```
┌──────────────────┐ ⇄ ┌──────────────────┐
│   Pane A (左)    │   │   Pane B (右)    │
│   D:\Program...  │   │   C:\Users\...   │
└──────────────────┘   └──────────────────┘
                  ↓ 点击 ⇄
┌──────────────────┐ ⇄ ┌──────────────────┐
│   Pane B (左)    │   │   Pane A (右)    │
│   C:\Users\...   │   │   D:\Program...  │
└──────────────────┘   └──────────────────┘
```

### 4.2 实现原理

交换操作的本质：**不移动任何 UI 元素，仅交换数据绑定的目标**。

```csharp
// PaneOrchestrator.SwapPanes()
public void SwapPanes()
{
    // 1. 交换 ViewModel 引用
    (ViewModel.Panes[0], ViewModel.Panes[1]) = (ViewModel.Panes[1], ViewModel.Panes[0]);

    // 2. 数据绑定自动驱动 UI 更新（MVVM 的自然优势）
    //    左侧 BrowserPane 的 DataContext → Panes[0]
    //    右侧 BrowserPane 的 DataContext → Panes[1]

    // 3. 持久化新的位置顺序
    ConfigService.Set(c => c.PaneOrder, new[] { Panes[0].Id, Panes[1].Id });
}
```

### 4.3 快捷键与附加手势
- **快捷键**: `Ctrl+Shift+S` (Swap) 或 `Ctrl+U`
- **拖拽手势**: 长按标签页拖向对侧面板可将其移入
- **按钮位置**: 居中于分割条上，仅在双列模式时可见

## 五、预览面板可组合化详细设计

### 5.1 核心理念

预览面板不再是"窗口右侧的一个固定区域"，而是**可以附加到任意 BrowserPane 上的独立子组件**。

### 5.2 附加模式

| 模式 | 描述 | 适用场景 |
|------|------|----------|
| **底部嵌入** | 预览面板嵌入在 BrowserPane 底部，通过一个可拖拽的水平分割条调整高度 | 默认模式，单列或双列均适用 |
| **侧面嵌入** | 预览面板嵌入在 BrowserPane 右侧，通过一个可拖拽的垂直分割条调整宽度 | 宽屏单列模式 |
| **无预览** | 该面板不附加预览 | 双列模式下只需一侧有预览 |

### 5.3 布局示例

**示例 1：单列 + 底部预览**（当前默认行为的组件化版本）
```
┌──────────────────────────────────┐
│  [BrowserPane]                   │
│  ┌────────────────────────────┐  │
│  │  TabBar                   │  │
│  │  AddressBar               │  │
│  │  FileList                 │  │
│  ├────────────────────────────┤  │  ← 水平分割条
│  │  [PreviewAttachment]      │  │
│  │  Preview + Notes + Info   │  │
│  └────────────────────────────┘  │
└──────────────────────────────────┘
```

**示例 2：双列 + 左侧面板带底部预览**
```
┌──────────────────┐ ⇄ ┌──────────────────┐
│  [BrowserPane A] │   │  [BrowserPane B] │
│  TabBar          │   │  TabBar          │
│  FileList        │   │  FileList        │
│  ──────────────  │   │                  │
│  [Preview]       │   │  (无预览)        │
└──────────────────┘   └──────────────────┘
```

**示例 3：双列 + 两侧都有底部预览**
```
┌──────────────────┐ ⇄ ┌──────────────────┐
│  [BrowserPane A] │   │  [BrowserPane B] │
│  FileList        │   │  FileList        │
│  ──────────────  │   │  ──────────────  │
│  [Preview A]     │   │  [Preview B]     │
└──────────────────┘   └──────────────────┘
```

### 5.4 触发方式

- 每个面板的工具栏上提供一个**预览切换按钮** `👁` 
- 右键面板标题栏 → "附加/分离预览面板"
- 全局快捷键 `Ctrl+P` 切换当前活动面板的预览显示

## 七、影响范围评估

### 需要修改的核心文件

| 层级 | 文件 | 改动类型 |
|------|------|----------|
| **Model** | `AppState.cs` | 重大 — `ColumnState` 改为 `PaneState[]` |
| **Model** | `AppConfig.cs` (ConfigManager.cs) | 重大 — 删除所有 `_Secondary` 字段，新增 `Panes[]` |
| **Config** | `ConfigMapper.cs` | 重大 — 重写映射逻辑为数组遍历 |
| **Config** | `ConfigurationService.cs` | 中等 — 适配新的存储结构 |
| **ViewModel** | `MainWindowViewModel.cs` | 重大 — `PrimaryPane`/`SecondaryPane` → `Panes[]` |
| **ViewModel** | `PaneViewModel.cs` | 中等 — 删除 `IsSecondary`，改为 `PaneIndex` |
| **ViewModel** | `RightPanelViewModel.cs` | 重大 — 拆解为 `PreviewAttachment` |
| **Handler** | `ColumnInteractionHandler.cs` | 简化 — 不再需要 `IsSecondaryPane()` |
| **Handler** | `LayoutEventHandler.cs` | 重大 — 重写双列管理逻辑 |
| **Handler** | `WindowLifecycleHandler.cs` | 中等 — 遍历 `Panes[]` 而非硬编码两个 |
| **Service** | `ColumnService.cs` | 简化 — 删除所有 `IsSecondary` 判断 |
| **Orchestrator** | `WindowOrchestrator.cs` | 重大 — 重写为 `PaneOrchestrator` |
| **Orchestrator** | `HandlerInitializer.cs` | 简化 — 循环创建而非硬编码两组 |
| **View** | `MainWindow.xaml` | 重大 — 面板区域改为 `ItemsControl` 或动态绑定 |
| **View** | `MainWindow.xaml.cs` | 大幅删减 — 绝大多数胶水代码回归 ViewModel |
| **Interface** | `IShellWindow.cs` | 简化 — 删除 `SecondFileBrowser` 等硬编码属性 |

### 预计代码量变化

- **删除**: ~800 行（冗余的 `_Secondary` 判断、双 Handler 胶水代码、旧配置字段）
- **新增**: ~400 行（`PaneContext` / `BrowserPane` 组件、`PaneOrchestrator`、`PreviewAttachment`）
- **净减少**: 约 400 行

## 八、风险与缓释措施

| 风险 | 等级 | 缓释 |
|------|------|------|
| 重构范围大，可能引入回归 Bug | 🔴 高 | 分 4 阶段渐进落地，每阶段独立验证 |
| 配置迁移可能丢失用户数据 | 🟡 中 | 程序未发布，无需向后兼容 |
| XAML 布局重构可能破坏视觉效果 | 🟡 中 | 第 3 阶段再动 XAML，前 2 阶段仅改 C# |
| `BrowserPane` 组件化后启动性能变化 | 🟢 低 | 延迟实例化第二面板（仅双列模式时创建） |

## 九、推荐方案

> **推荐采用方案 C（混合策略）**。
>
> 它以方案 B 的组件化自治为最终目标（彻底消灭主/副概念），同时采用方案 A 的分阶段节奏，确保每个中间状态都是可编译、可运行、可回退的。
>
> 阶段 1（配置统一）和阶段 2（PaneContext + 面板交换）可以在一次集中冲刺中完成，快速兑现用户可感知的价值（交换按钮）。阶段 3–4 作为后续打磨进行。

## 十、已确认的架构决策

> 以下决策于 2026-03-02 由项目负责人确认。

| # | 议题 | 决策 |
|---|------|------|
| 1 | **面板命名** | 采用 **Pane A / Pane B**，代码层使用 `Panes[0]` / `Panes[1]` 索引 |
| 2 | **预览面板归属** | 默认附加到**各自面板的文件信息区右侧**；可根据模式切换（预览模式、双栏模式等）自动调整位置和尺寸，即预览窗口可变大变小、可跨面板流动 |
| 3 | **单列回退** | 关闭双列模式时，**保留当前活动面板**的状态 |
| 4 | **方案选择** | 采用 **方案 B（深度重构）**，在 `refactor/view-componentization` 分支上一次性施工完成 |
