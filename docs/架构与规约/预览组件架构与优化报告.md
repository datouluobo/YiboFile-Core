# YiboFile 预览组件架构审查与优化报告

## 1. 现状架构审查 (Current Architecture Review)

YiboFile 的预览子系统目前采用了 **MVVM + 简单工厂 + 弱聚合消息总线** 的三层架构，整体设计初衷是为了解耦各类型预览的实现逻辑。当前支持约 15 种核心预览类型的视图流转。

**数据流转链路：**
选中的文件变更 (`FileSelectionChangedMessage`) 触发 `RightPanelViewModel` 进行防抖处理 (250ms) -> 发送 `PreviewRequestMessage` -> `PreviewService` 进行快/慢加载并行策略 (50ms) 缓冲 -> `PreviewFactory` 实例化对应格式的 ViewModel -> 发送 `PreviewChangedMessage` 回 `RightPanelViewModel` -> 通过 `RightPanelControl.xaml` 的 implicit `DataTemplate` 映射并渲染具体控件。

### 当前架构亮点：
1. **防闪烁加载机制**：`PreviewService` 采用 50ms 延迟判定，对于小文件直接渲染，避免进度条闪烁提升了视觉平滑度。
2. **防抖与中断管控**：基于 `CancellationToken` 贯穿异步链路，结合生成计数器 (`_currentGeneration`) 防止快速切换引发的状态覆盖。

## 2. 发现的核心缺陷审计 (Core Defects Audit)

在代码级扫描中，发现了若干不符合框架稳健性与 MVVM 扩展性的严峻问题：

### 🔴 严峻缺陷 (P0 级)
1. **原生控件资源与句柄泄漏**：
   - 现有的 `IPreviewViewModel` 和 `BasePreviewViewModel` 均未实现 `IDisposable` 接口。
   - `WebView2`（用于 Markdown, Word, Excel, Pdf, CAD, Chm）以及 `LibVLC`（用于视频）等重型非托管资源的宿主控件，在 ViewModel 切出后未进行 `Dispose()` 显式的释放销毁。
   - `MarkdownPreviewControl` 的 `DataContextChanged` 事件进行了 `+= PropertyChanged` 挂载，切出时未注销（-=）引发事件泄漏。

### 🟡 架构耦合缺陷 (P1 级)
2. **违反 MVVM 隔离准则**：
   - `PreviewFactory` 中硬编码了 `OnFileListRefreshRequested` 和 `OnOpenFolderInNewTab` 静态回调（Action）。工厂层直接控制 UI 逻辑回调，导致底层类与应用层表现层产生了双向黏连。

### 🟢 业务逻辑分歧 (P2 级)
3. **元数据解析职责破窗**：
   - 系统中存在两个管理文件类型的集散地：`FileTypeManager` 和 `PreviewFactory`。例如 `.ai` 文件在管理器中标记为 `CanPreview = false`，但工厂的魔术字符串映射表里却包含了它；`.apk` 被误标为 `Executable`，但对应源码又尝试按 `Archive` 对待。

## 3. 重构决策与多维方案对比分析

为了解决上述的最核心问题（系统崩溃与内存泄漏风险、降低架构耦合），此处严格遵循多维方案比对原则，提出以下重构设计：

### 决议任务一：基于 WebView2/VLC 重型组件的内存泄漏问题修复

#### 🔺 方案 A：生命周期级借口约定（显式释放模式）
**思路：** 在 `IPreviewViewModel` 契约中引入明确的 `IDisposable`（或 `ICleanup`）。在 `RightPanelViewModel` 中，当 `ActivePreview` Property 被赋新值前，检查旧值并显式调用 `Dispose()`。在所有的 `Control` 中订阅 `Unloaded` 事件主动释放 `WebView2`/`LibVLC` 实例。
- **优点**：控制极其精准，确定性最高。符合标准 C# 托管与非托管资源清理模式。
- **缺点**：有侵入性，所有相关的 ViewModel 均需补充实现清理逻辑，重构涉及文件较多。

#### 🔺 方案 B：依赖 Attached Behaviors 的视觉树感知回收（自动清理模式）
**思路：** 编写一个自定义的附加行为 `PreviewCleanupBehavior`，通过附加属性绑定至各级的承载容器（如 `ContentPresenter`）。当承载的 DataContext 卸载或发生突变时，底层通过反射或接口寻找并销毁重型 Component 句柄，而不干预 ViewModels。
- **优点**：UI 与逻辑完全断开，ViewModels 层面依然保持极简；不需要大规模修改现有的 `ViewModel` 继承体系。
- **缺点**：WPF 视觉树回收时序可能因虚拟化产生不确定延迟；隐藏了关键清理逻辑，增加后期的调试排障难度。

**专家推荐**：实施**方案 A**。对于 `WebView2` 这样的 COM 包装内核层进程，其内存模型庞大，必须确保严格而具体的 `Dispose`，避免依赖不可控的 WPF Behavior 延迟生命周期。

---

### 决议任务二：`PreviewFactory` 静态回调（MVVM 污染）解耦

#### 🔺 方案 A：全面重构为基于事件总线 (EventBus) 解聚
**思路：** 废除 `PreviewFactory` 中的两个 `static Action`。在所有的 `PreviewXXXViewModel` 中，如果需要请求父刷新或新开标签，直接注入或使用 `_messageBus.Publish(new FileListRefreshRequestMessage())`。
- **优点**：贯彻了已有的弱耦合事件机制，工厂类只负责实例化 ViewModel 本职工作，消除硬编码污染。
- **缺点**：增加了消息类型的梳理成本（需要额外定义 2 个 Message Class）。

#### 🔺 方案 B：依赖注入（工厂升级为 `IPreviewFactory` 服务）
**思路：** 消除静态类 `PreviewFactory`，将其升级并注册至 IoC 容器作为 `IPreviewFactory` 服务。所有需要操作的上下文（如打开标签服务的接口）在构造时注入到该实例化工厂中，再通过工厂流转至生成的 ViewModel 里去。
- **优点**：实现了测试的完全 Mock 化和强接口契约约束，属于重型企业级应用的标配。
- **缺点**：对于目前仅起简单转发作用的静态辅助类来说，将其服务化会导致过度设计。

**专家推荐**：实施**方案 A**。考虑到当前项目中已成熟引用的 `IMessageBus`，且修改和扩增 Message 最为轻量且维持了范式的纯粹性。
